## What Millhaven actually is

A UE 5.8 C++ open-world village where **the entire world is generated procedurally at
runtime** — no `.uasset` content, no Blueprints, no input assets. It runs from an empty
level. Full architecture notes are in `CLAUDE.md`; the project's own `README.md` is
genuinely good and accurate, which is rarer than it should be.

I read all 13 source files. Impressions:

- The code is **better than "prototype quality"**. `TerrainHeight` being a pure static
  function is a real design decision, not an accident — it means mesh generation, prop
  placement and player spawn agree with each other with no raycasts and no ordering
  problem. Colour-batched procedural mesh sections are the right call for flat-shaded
  low-poly.
- The UE 5.8 hardening pass documented in README §8 is the most valuable thing in the
  repo. Most of those fixes (GC-invisible statics, the `Role` shadow, the dialogue
  use-after-free, the collapsing PRNG seed) are bugs that would have taken hours to find
  at runtime. I've lifted them into `CLAUDE.md` §5 as a regression list, because they
  read like arbitrary style choices to anyone who wasn't there.
- **`Tools/check_sources.py` passes**: 13 files, 0 errors, 0 warnings. Verified by
  running it. It is a static linter, not a test, and the README is appropriately humble
  about how weak a signal it is.

## The thing I'd flag hardest

**`codex/create-npc-communication-file-with-qwen2.5-7b-instruct` is a Unity project.**

`Assets/Scripts/QwenNpcDialogue.cs` is a `MonoBehaviour` using `UnityEngine` and
`UnityEngine.Networking`. It wires an NPC to a Qwen2.5-7B-Instruct chat endpoint for
live LLM dialogue. There's a .NET 8 console tester alongside it.

It is well-written and the character prompt (Liora, a beekeeper) is nicely done. But it
cannot run in this project. It is a different engine, a different language runtime, a
different NPC cast, and a different dialogue architecture — networked LLM inference
versus Millhaven's hand-authored `TMap<FName, FDlgNode>` trees. It also introduces an
outbound API dependency and an API key, neither of which exists anywhere else here.

I don't know whether this was an experiment you'd abandoned, a deliberate parallel
track, or a tool that got pointed at the wrong repo. I've put it in the backlog as a
decision for you rather than guessing. It's the single biggest open question in the
repo — the *idea* (LLM-driven NPC conversation) is compelling and would be a genuinely
strong direction for Millhaven, but it would need rebuilding in UE5 C++ from scratch,
and that's an architecture call, not a chore.
